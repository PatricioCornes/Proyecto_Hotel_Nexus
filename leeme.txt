# BITÁCORA TÉCNICA - HOTEL NEXUS

Fecha de inicio de la integración: 13-07-2026
Contexto: Evaluación transversal DUOC UC

======================================================================
1. OBJETIVO
======================================================================

Integrar los siete microservicios del proyecto Hotel Nexus para que el
proceso hotelero completo funcione de manera coordinada:

- Reservas y pagos.
- Asignación y estados de habitaciones.
- Check-in y check-out.
- Limpieza y asignación de personal.
- Consumos de restaurante.
- Uso y cobro de estacionamiento.
- Facturación final consolidada.

La solución usa dos formas de comunicación:

1) RabbitMQ para eventos de negocio que pueden tener varios consumidores.
2) REST para comandos o consultas que necesitan una respuesta inmediata.

Esta combinación evita convertir todo el sistema en una cadena de llamadas
síncronas y mantiene explícitos los contratos entre servicios.

======================================================================
2. ESTADO BASE ENCONTRADO ANTES DE LOS CAMBIOS
======================================================================

El repositorio contenía siete aplicaciones Spring Boot 4.0.6 / Java 21,
cada una con su propio pom.xml, puerto y conexión JPA/MySQL:

- Staff:        puerto 8080, base db_nexus_staff.
- Rooms:        puerto 8081, base db_hotel_nexus.
- Restaurant:   puerto 8082, base restaurant.
- Reservation:  puerto 8083, base db_nexus_reservation.
- Payments:     puerto 8084, base payments.
- Garage:       puerto 8085, base db_nexus_garage.
- Cleaning:     puerto 8086, base cleaning.

Todos tenían una estructura CRUD básica de controlador, servicio,
repositorio y entidad. No existían API Gateway, broker de eventos,
orquestación general, factura consolidada ni contratos compartidos.

En el código inspeccionado, la única comunicación remota explícita era un
cliente Feign desde Reservation hacia Rooms. Payments todavía era un CRUD
aislado, por lo que una aprobación no confirmaba realmente una reserva.

Problemas relevantes del estado inicial:

- Reservation confundía el número visible de habitación (por ejemplo 101)
  con el ID interno de la tabla y exigía IDs entre 100 y 200.
- Rooms tenía un setNumero manual que siempre lanzaba
  UnsupportedOperationException al actualizar.
- Una reserva comprobaba disponibilidad antes del pago, pero no existía una
  asignación atómica al confirmarla.
- No existían eventos entre procesos.
- Cleaning guardaba un habitacionId, pero no consultaba Rooms ni Staff.
- Restaurant no tenía consumos asociados a una estadía.
- Garage administraba plazas, pero no modelaba un uso facturable.
- Staff no tenía estado de disponibilidad.
- Payments no relacionaba pagos con reservas ni consolidaba cargos.
- Los tests existentes sólo eran contextLoads y requerían infraestructura.
- Los scripts mvnw.cmd fallaban en PowerShell cuando ~/.m2 no era un enlace.
- Sólo Reservation y Staff tenían Dockerfile; no existía compose general.

======================================================================
3. ARQUITECTURA IMPLEMENTADA
======================================================================

                         RabbitMQ: nexus.events
                                   |
        +--------------------------+---------------------------+
        |                          |                           |
    Reservation                 Cleaning                   Payments
        |                          |                           |
        +--> Rooms (asignar)       +--> Staff (asignar)        +--> Reservation (cargo)
        +--> Payments (reembolso)  +--> Staff (liberar)        +--> Restaurant (total)
                                                               +--> Garage (total)

Regla utilizada:

- Evento RabbitMQ: informa un hecho ya confirmado y puede despertar a más
  de un servicio.
- REST interno: ejecuta una operación que necesita respuesta inmediata,
  como reservar una habitación o asignar un empleado concreto.

Los eventos se publican después del commit de la transacción local. De esta
forma, otro microservicio no recibe un hecho cuya escritura todavía podría
revertirse.

Exchange RabbitMQ: nexus.events (topic, durable)

Eventos implementados:

- ReservationCreated
  Routing key: reservation.created
  Productor: Reservation.
  Se emite después de crear una reserva PENDIENTE_PAGO.

- PaymentCompleted
  Routing key: payment.completed
  Productor: Payments.
  Consumidor: Reservation.
  Si aprobado=true, Reservation asigna una habitación y se confirma.

- CheckInCompleted
  Routing key: stay.checkin.completed
  Productor: Reservation.
  Consumidor: Rooms.
  Rooms cambia la habitación desde Reservada a Ocupada.

- CheckOutCompleted
  Routing key: stay.checkout.completed
  Productor: Reservation.
  Consumidores: Rooms, Cleaning y Payments (cada uno tiene su propia cola).
  Rooms marca Sucia, Cleaning crea/asigna tarea y Payments genera factura.

- CleaningRequested
  Routing key: cleaning.requested
  Productor: Cleaning.
  Registra que la tarea fue creada y ya tiene empleado asignado.

- CleaningFinished
  Routing key: cleaning.finished
  Productor: Cleaning.
  Consumidor: Rooms.
  Rooms vuelve a dejar la habitación Disponible.

Colas durables creadas:

- reservations.payment-events
- rooms.stay-events
- rooms.cleaning-events
- cleaning.checkout-events
- payments.checkout-events

======================================================================
4. REGLAS DE NEGOCIO IMPLEMENTADAS
======================================================================

4.1 Reserva, pago y asignación

- Una reserva nueva queda PENDIENTE_PAGO y todavía no posee habitación.
- Payments recibe una aprobación relacionada con codigoReserva.
- Payments guarda el pago APROBADO y emite PaymentCompleted.
- Reservation consume el evento de forma idempotente.
- Rooms selecciona con bloqueo pesimista la primera habitación Disponible
  del tipo solicitado. Así se evita asignar la misma habitación a dos pagos
  procesados simultáneamente.
- La tarifa por noche se copia a la reserva al confirmar. Esto conserva el
  precio histórico aunque luego cambie el precio de Rooms.
- Estados de reserva usados: PENDIENTE_PAGO, CONFIRMADA, OCUPADA,
  FINALIZADA y CANCELADA.

4.2 Cancelaciones y reembolsos

- 7 días o más de anticipación: 100%.
- Entre 2 y 6 días: 50%.
- Menos de 2 días: 0%.
- Reservation solicita el reembolso a Payments.
- Si ya había habitación asignada, vuelve a Disponible.
- Payments guarda el movimiento con tipo REEMBOLSO para mantener trazabilidad.

4.3 Estados de habitación

Estados controlados por el flujo:

- Disponible -> Reservada: pago aprobado y asignación.
- Reservada -> Ocupada: CheckInCompleted.
- Ocupada -> Sucia: CheckOutCompleted.
- Sucia -> Disponible: CleaningFinished.
- En Mantenimiento sigue disponible como estado administrativo mediante el
  CRUD de Rooms y no participa en asignación automática.

4.4 Limpieza y personal

- CheckOutCompleted genera una tarea de limpieza una sola vez por reserva.
- Cleaning solicita a Staff un empleado disponible con cargo LIMPIEZA.
- Staff bloquea al empleado y cambia disponible=false.
- La tarea queda ASIGNADA con habitacionId, reservaCodigo y empleadoId.
- Al finalizar, Staff libera al empleado y Cleaning emite CleaningFinished.

4.5 Restaurante

- Se agregó el concepto Consumo.
- Cada consumo contiene reservaCodigo, descripción, monto y fecha.
- La suma por reserva es consultada por Payments para la factura final.

4.6 Garage

- Se agregó UsoEstacionamiento, separado del catálogo de plazas existente.
- Registra reservaCodigo, patente, entrada, salida y tarifa por hora.
- Al marcar salida calcula horas hacia arriba, con mínimo de una hora.
- Si la factura se consulta con un uso todavía abierto, calcula el costo
  acumulado hasta ese momento.

4.7 Facturación final

- Payments consume CheckOutCompleted y consulta los subtotales de Reservation,
  Restaurant y Garage.
- También suma cargos adicionales registrados directamente en Payments.
- Se persiste una FacturaFinal única por codigoReserva.
- Repetir la consolidación actualiza la misma factura (operación idempotente).
- Campos: habitación, restaurante, estacionamiento, servicios adicionales,
  total, pagado y saldo.

7. CÓMO LEVANTAR EL PROYECTO
======================================================================

Requisitos:

- Java 21 o superior (los pom compilan con release 21).
- MySQL accesible en localhost:3306.
- RabbitMQ accesible en localhost:5672.
- Maven no necesita instalarse globalmente: cada servicio tiene mvnw.cmd.

Opción A: levantar sólo infraestructura y ejecutar los servicios desde el IDE:

    docker compose up -d mysql rabbitmq

Panel RabbitMQ:

    http://localhost:15672
    usuario: guest
    clave: guest

Si MySQL ya está instalado y contiene las bases del proyecto:

    docker compose up -d rabbitmq

Luego iniciar cada aplicación desde el IDE o en siete terminales con:

    .\mvnw.cmd spring-boot:run

Usar como directorio de cada terminal la carpeta que contiene el pom.xml del
servicio correspondiente. Orden recomendado:

1) Staff, Rooms, Restaurant y Garage.
2) Cleaning y Payments.
3) Reservation.

Opción B: ejecutar todo el sistema con Docker Compose:

Primero generar los JAR de cada servicio desde su carpeta:

    .\mvnw.cmd -DskipTests package

Después, desde la raíz del repositorio:

    docker compose up -d --build

Para comprobar estados y consultar logs:

    docker compose ps
    docker compose logs -f

Para detener el sistema sin borrar los datos:

    docker compose down

Las propiedades aceptan variables como SPRING_DATASOURCE_URL,
SPRING_DATASOURCE_USERNAME, SPRING_DATASOURCE_PASSWORD,
SPRING_RABBITMQ_HOST, ROOMS_SERVICE_URL, PAYMENTS_SERVICE_URL,
STAFF_SERVICE_URL, RESERVATIONS_SERVICE_URL, RESTAURANT_SERVICE_URL y
GARAGE_SERVICE_URL.

8. GUIÓN DE DEMOSTRACIÓN END-TO-END
======================================================================

Las fechas del ejemplo deben reemplazarse por fechas futuras.

1) Crear empleado de limpieza:

curl.exe -X POST http://localhost:8080/empleados `
  -H "Content-Type: application/json" `
  -d "{\"run\":\"12345678-9\",\"nombre\":\"Ana\",\"apellido\":\"López\",\"fechaNacimiento\":\"1990-01-01\",\"correo\":\"ana@nexus.cl\",\"telefono\":\"999999999\",\"turno\":\"DIA\",\"cargo\":\"LIMPIEZA\"}"

2) Verificar que existe una habitación Disponible del tipo Doble. El seeder
   de Rooms crea la habitación 101 si no existe.

3) Crear reserva:

curl.exe -X POST http://localhost:8083/reservaciones `
  -H "Content-Type: application/json" `
  -d "{\"clienteId\":\"CLI-001\",\"tipoHabitacion\":\"Doble\",\"fechaIngreso\":\"2026-08-10\",\"fechaSalida\":\"2026-08-13\"}"

Guardar id y codigoReserva de la respuesta.

4) Aprobar pago usando el codigoReserva:

curl.exe -X POST http://localhost:8084/pagos/reservas/RES-XXXXXXXX/aprobar `
  -H "Content-Type: application/json" `
  -d "{\"monto\":120000,\"metodo\":\"TARJETA\"}"

PaymentCompleted viaja por RabbitMQ. Al consultar la reserva debe estar
CONFIRMADA y tener habitacionId.

5) Check-in:

curl.exe -X POST http://localhost:8083/reservaciones/1/check-in

La habitación pasa a Ocupada mediante CheckInCompleted.

6) Cargar consumo de restaurante:

curl.exe -X POST http://localhost:8082/consumos `
  -H "Content-Type: application/json" `
  -d "{\"reservaCodigo\":\"RES-XXXXXXXX\",\"descripcion\":\"Cena\",\"monto\":25000}"

7) Registrar estacionamiento y guardar el id retornado:

curl.exe -X POST http://localhost:8085/usos-estacionamiento `
  -H "Content-Type: application/json" `
  -d "{\"reservaCodigo\":\"RES-XXXXXXXX\",\"patente\":\"ABCD12\",\"tarifaHora\":2000}"

Finalizar el uso:

curl.exe -X POST http://localhost:8085/usos-estacionamiento/1/salida

8) Agregar un servicio adicional opcional:

curl.exe -X POST http://localhost:8084/cargos-adicionales `
  -H "Content-Type: application/json" `
  -d "{\"reservaCodigo\":\"RES-XXXXXXXX\",\"descripcion\":\"Lavandería\",\"monto\":8000}"

9) Check-out:

curl.exe -X POST http://localhost:8083/reservaciones/1/check-out

Este único comando produce tres efectos asincrónicos:

- Rooms deja la habitación Sucia.
- Cleaning crea tarea y Staff deja al empleado no disponible.
- Payments consolida y guarda FacturaFinal.

10) Consultar factura (también fuerza una actualización de subtotales):

curl.exe http://localhost:8084/facturas/reserva/RES-XXXXXXXX

11) Consultar tareas y finalizar la asignada:

curl.exe http://localhost:8086/limpiezas
curl.exe -X POST http://localhost:8086/limpiezas/1/finalizar

CleaningFinished libera al empleado y Rooms deja la habitación Disponible.

11.2 Incidencias reales encontradas y corregidas

Incidencia 1 - Payments y Cleaning no iniciaban

Síntoma:

    No qualifying bean of type RestClient.Builder available

Causa: con las dependencias actuales, Spring Boot 4 no registró
automáticamente RestClient.Builder como bean.

Corrección:

- FacturacionServicio y LimpiezaServicio ahora crean clientes con
  RestClient.builder().baseUrl(...).build().
- Ambos servicios fueron recompilados, reconstruidos y arrancaron conectados
  a MySQL y RabbitMQ.

Incidencia 2 - HTTP 500 al crear una reserva

Síntoma SQL:

    Column 'habitacion_id' cannot be null

Causa: el modelo antiguo exigía una habitación al insertar, pero el nuevo
flujo requiere crear PENDIENTE_PAGO sin asignación y asignar después del pago.

Corrección:

- Se eliminó nullable=false de Reservacion.habitacionId.
- En el esquema de prueba se migró habitacion_id a BIGINT NULL.
- Tras repetir, la reserva se creó sin habitación y PaymentCompleted la
  confirmó/asignó correctamente.

Incidencia 3 - HTTP 500 al cancelar una reserva

Síntoma: el Feign client de Reservation recibía 404 al pedir el reembolso.

Causa: el contrato no incluía el prefijo /pagos del PagoControlador.

Corrección:

- Ruta definitiva: POST /pagos/reservas/{codigo}/reembolso.
- PagoClient y PagoControlador fueron alineados y reconstruidos.
- La repetición generó correctamente el reembolso completo.

Rooms:

Staff:

Restaurant:

- reservaCodigo, descripción y monto obligatorios.

Garage:

- patente normalizada y con patrón permitido.
- tarifa por hora positiva.
